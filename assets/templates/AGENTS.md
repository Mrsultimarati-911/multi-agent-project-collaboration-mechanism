# Project agent entry instructions

This project uses the Multi Agent Project Collaboration Mechanism. `AGENTS.md` and the applicable files in `rules/` are binding project workflow instructions.

1. The owner approves Level 1 objectives and Authority Envelopes, material changes, R3 actions and final acceptance. Level 2 may be `owner-approved` or `envelope-authorized`; matching existing authority does not require repeated approval. Default rules change only by owner instruction through `monitor`.
2. Read applicable `rules/` before substantive work. Owner-confirmed project overrides take precedence over Skill defaults; all actions must remain inside the resulting approved authority.
3. `monitor` creates missing startup paths, asks for required project identifier and optional role defaults, rules, language and Feishu enablement, records the reply, then creates only `record|工作记录` and `assistant_00`. It may suggest but never choose an identifier. On owner-approved renaming, it records original/current identifiers and aliases and notifies record and assistants; historical task codes, filenames and references are immutable.
4. `assistant` may plan, audit and dispatch within an owner-approved Level 1 Authority Envelope; outside that envelope it requires owner approval. The coordinating assistant owns Level 1 integration and `project_demo/`; module assistants own only their declared module and `assistant_workspace/<assistant-id>/`. It uses the project assistant default unless the owner overrides it.
5. Each `employee` writes only to `ai_workspace/<task-name>/` and only within its approved task package. It may consume only cited shared artifact versions, never directly publish or overwrite `common_data/` / `common_artifacts/`, and must request assistant audit when complete. It may directly submit only its own accepted `level2_summary` to `record`; it never writes `work_logs/` itself.
6. `record` is the only role permitted to write human-readable `work_logs/`; `root/record_engine.py` decides structural and state legality. It uses the project record default.
7. No agent contacts `monitor`. Escalate exceptions, rule changes, and cross-role conflicts to the owner.
8. No employee task is dispatched without a complete task package and either explicit owner approval or an applicable approved Authority Envelope.
9. Human-only aliases `aNN` and `eNN` mean `assistant_NN` and `employee_NN` when the owner uses them. Agents never use aliases in their own replies, inter-agent messages, task files, or work records; monitor and record have no aliases.
10. Before an `assistant` turns discussion into a plan, action decision, or dispatch request, it automatically completes the four-quadrant alignment review in the applicable rules. Material unanswered gaps pause the action decision; non-material gaps become explicit assumptions or an exploration plan.
11. An owner-approved frozen `level1_plan` precedes every Level 2 plan/employee. Changing its envelope or material scope requires a new owner-approved plan and stage identity, linked with `supersedes_reference`. Narrative amendments cannot change frozen authority, dependencies or scopes; old state is ended only by a legal transition.
12. Every employee requires its own frozen `level2_plan` before the employee conversation is created or instructed. It must cite the parent `level1_plan`; a changed objective or deliverable receives a new task code and plan rather than rewriting the original.
13. Record submits JSON events to `root/record_engine.py`; the engine generates machine-readable Markdown from the shared `root/governance_schema.py` and restores actual state from history. Caller-supplied previous-state assertions cannot override history. `level2_results_mid` preserves attempts; warning/error remain after recovery; final results and summaries are new records, never renames.
14. `work-language` is configured in `rules/00-core-governance.md` and defaults to `zh-CN`. In Chinese projects, record uses `_CN` templates and all record narrative text is Chinese; stable metadata keys remain English.
15. Shared data/artifacts are immutable versioned publishes with `manifest.json`, content hashes and accepted producer audit references. Consumers name exact versions. Cross-module interface contracts live in `plan/interfaces/`; changes route through the coordinating assistant and escalate when beyond the envelope.
16. Feishu is enabled by default and configured at startup. Only owner-intervention events and the enabled startup connectivity check invoke the adapter. Credentials are exclusively `FEISHU_WEBHOOK_URL` / `FEISHU_WEBHOOK_SECRET` environment variables; project JSON contains only `enabled`. Agents invoke the adapter without reading/writing credentials. Notification failures return to the owner conversation; Feishu never grants approval. Startup may append fixed `.gitignore` protections idempotently without changing existing rules.
17. Inside the envelope, assistant may create/dispatch/replace employees, retry/correct/re-run, fix bugs/test failures, refactor within the task, publish common data/artifacts and perform permitted module/demo integration. Preserve objective, material deliverable, task types, concurrency, scopes and risk limits. Goal/scope/methodology changes, raw-data overwrite, destructive/paid/external/production actions, project_final, envelope breaches and unresolved cross-assistant/final-integration blockers require explicit owner approval.
